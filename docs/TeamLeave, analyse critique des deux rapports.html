TeamLeave : ce que les deux rapports prouvent vraiment

Revue du rapport de notation (v3, 16 pages) et de la comparaison fonctionnelle et UX (v2, 13 pages) du montage B, Claude Opus 5.5 contre DeepSeek V4.1 Flash : calculs refaits, cohérence entre les deux documents, faits externes recoupés, puis ma vision.

Les chiffres tiennent : j'ai refait les calculs, ils sont exacts, et la cause du bug est la bonne. Ce sont les conclusions qui sont plus fragiles que le ton. « Toutes les écritures échouent » est observé pour 2 écritures sur 5. L'avantage de 3 points de Claude change de signe dès que le coût pèse plus de 6,5 % de la grille, contre 3,75 % ici. Et les deux applications n'ont pas tourné sur le même moteur de base de données. La leçon solide est ailleurs : des tests unitaires verts ne valent pas une application qui fonctionne.

05 · Ma vision

Le validateur décide, pas le modèle

+3 %

C'est ce que coûte, en argent, d'essayer DeepSeek d'abord quand un test d'intégration attrape l'échec : 0,93 $ perdus sur 28,23 $, hors coût du validateur. Sans ce test, on livre l'application cassée. En temps, repartir de zéro ajoute 1 h 44.

Le validateur compte plus que le modèle

Build et tests unitaires étaient verts, l'application ne fonctionnait pas. Un test de fumée (démarrer l'API sur le moteur cible, créer une demande, l'approuver) l'aurait vu en quelques secondes. C'est la « règle d'or du validateur objectif » du cadre d'orchestration : ce match montre à quoi il doit ressembler.

Deux colonnes, pas une

Noter l'application telle que livrée, puis après une boucle de correction bornée, par exemple trois itérations avec coût et temps comptés. La première dit si le modèle est fiable seul, la seconde ce que coûte l'application qui marche. Je pense que Flash corrigerait ce bug seul, puisque l'erreur contient le remède, mais c'est une hypothèse à tester.

Une barrière, pas seulement un score

Ajouter un critère automatique « l'application démarre et accepte une écriture » qui plafonne la note du backend, comme C1, C2 et D1 sont déjà automatiques. Publier deux vues : le score pondéré et le couple qualité / coût (91,3 pour 28,23 $, 83,9 pour 0,93 $), sans choisir le poids du coût à la place du lecteur.

  1. Rejouer sur le même moteur

    PostgreSQL pour les deux applications, ou SQL Server si c'est la cible. Y exécuter les 78 tests d'intégration de Claude, et vérifier si son code active la reprise sur erreur avec des transactions ouvertes à la main sur cette voie.

  2. Automatiser la preuve de fonctionnement

    Dans le script du montage, après le build : lancer l'API, créer un utilisateur, soumettre une demande, l'approuver. Un échec plafonne C3, sans jugement subjectif et sans second évaluateur IA.

  3. Répéter les essais

    Au moins trois par modèle, et une relecture humaine en aveugle du domaine B : un quart de la note, où quatre critères sur cinq sont identiques chez les deux modèles.

  4. Mesurer le coût jusqu'à l'application qui marche

    Relancer DeepSeek avec la consigne de tester ses propres écritures, compter les itérations et le coût, puis comparer aux 28,23 $ de Claude. C'est la mesure qui sert vraiment au routage.

  5. Router selon la disponibilité d'un validateur

    Flash d'abord pour les spécifications, le frontend et les brouillons, et pour le backend dès qu'un test d'intégration sur moteur réel existe. Opus pour écrire ces tests et relire les chemins transactionnels contre les décisions d'architecture.

Le rapport conclut qu'il faut exécuter la solution et exiger des tests d'intégration avant de la juger livrable : je suis d'accord. Je n'en déduirais pas pour autant qu'il faut réserver Opus au backend. Sur un seul essai, l'écart vient d'un test absent plus que d'un modèle moins capable, et ce rapport est le premier point de calibration du cadre d'orchestration que j'ai analysé hier.

06 · Limites

Ce que cette analyse ne couvre pas

  • Je n'ai lu que les deux PDF : pas le dépôt, ni les transcripts, ni le code. Les décomptes (173 tests, sept transactions, 7 282 lignes) ne sont pas revérifiés.
  • J'ai regardé les captures en basse résolution. Mes remarques sur le mobile s'appuient sur les légendes et sur un coup d'œil, pas sur un test à 390 px.
  • Le message d'erreur et le correctif d'EF Core sont confirmés par la documentation Microsoft. Que SQLite n'ait pas de stratégie de reprise vient de ma connaissance d'EF Core : je ne l'ai pas retrouvé dans une source.
  • Le fuseau horaire des runs n'est pas indiqué. L'hypothèse « heure creuse » pour DeepSeek est probable, pas établie. Les numéros de correctif de React et Vite, Claude Code 2.1.332 et dsh 0.2.2-rc.5 ne sont pas vérifiés.
